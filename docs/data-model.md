# Дані та атомарні операції

Авторитетна схема: SPEC.md §§5–7; фактичні Rules — один кореневий firestore.rules. Вони використовуються і тестами, і firebase.json. Прикладні production-дані цього оновлення не створювались.

- users: приватний профіль, роль organizer/admin/developer, isDisabled. Самореєстрація створює лише organizer; клієнт не може призначати роль. Admin може змінювати isDisabled організатора разом з adminAudit.
- rooms: публічне читання тільки active; admin бачить всі. revision/lastAuditId пов’язують кожну зміну з незмінним adminAudit. Архівування не видаляє опубліковані події.
- bookings: приватні заявки; owner або admin. `responsibleName` — публічне ім’я відповідального. version і очікувана версія запобігають перезапису чужого рішення. history/{version} обов’язкова й незмінна. Щотижневий повтор — кілька звичайних заявок, без окремої колекції серій.
- publicEvents: лише точна публічна проєкція approved booking, включно з `responsibleName`; UID, контакти, причини відхилення/скасування не копіюються.
- rooms/{roomId}/occupancy/{blockId}: UTC блок 6 годин, 12 півгодинних слотів. ID — Unix seconds початку блока. lastMutationBookingId, lastMutationVersion, updatedAt/By підтверджують ту саму транзакцію. Повна перевірка вільності/власності й незмінності сторонніх слотів — у Rules; [обґрунтування](decisions/003-occupancy-version-witness.md).
- supportTickets: версіоновані звернення; тільки admin/developer. comments append-only, history/{version} append-only, attachments append-only (JPEG/PNG/WebP ≤700 КБ, до 5 на звернення). Статус, priority, коментар та history змінюються атомарно. Підтримка не надає developer прав бронювання/керування користувачами.

BookingService спершу читає всі потрібні documents, потім записує booking/history, до чотирьох occupancy блоків і publicEvents. Pending не створює locks. Cancellation видаляє публічну проєкцію і звільняє тільки власні slots. Якщо транзакція відхилена, часткових змін немає.

SupportRepository має один transactional write path. Reopen потребує нового коментаря; конкурентна дія зі старою версією завершується staleVersion. Введений текст у формі зберігається для повтору після оновлення.

DTO перевіряють schemaVersion та типи. Час зберігається UTC; Flutter показує Europe/Kyiv. Firestore зберігає microsecond precision, тому серверний тест дрібного відхилення використовує 1000 ns, а не 1 ns, який Firestore округлює: https://firebase.google.com/docs/firestore/manage-data/data-types.

Пагінація: limit 25, максимум 100; сортування з documentId як стабільним tie-breaker. «Мої заявки» — startAt від сьогодні ASC. Calendar читає bounded range зі startAt lookback 6h і відсікає події, що вже завершилися до початку вікна. Усі composite indexes для реалізованих запитів — у firestore.indexes.json. No persistence у Firestore Web; приватні екрани демонтуються при logout/втраті дозволів.

Firebase Console та Admin SDK обходять Rules: власник має окремо дотримуватись зв’язності даних. Клієнтські Rules не захищають від помилкового адміністративного імпорту.

## Розширення за зверненнями MI — 14.10.2026

- `users.canPublish`: необов'язкове boolean-поле для сумісності з існуючими профілями; відсутність означає false. Надання/відкликання — тільки admin організатору, зі збільшенням adminRevision й точним adminAudit `set_publishing`. Самореєстрація не може встановити true. Дозвіл не змінює роль та не відкриває чужі заявки.
- `bookings.status = deleted`, `lastAction = delete`: термінальний стан для видалення помилкових подій з інтерфейсу. Перехід дозволений admin або власнику з canPublish; змінюються лише статус і службові поля версії/актора/часу. Та сама транзакція звільняє слоти, видаляє publicEvents і пише history. Дані й аудит не знищуються; повернення з deleted не дозволено. Репозиторій не повертає deleted у деталі та списки, але продовжує пагінацію за оригінальним курсором.
- Щотижневі ID мають вигляд `<20-символьний Firestore ID>-YYYYMMDD`; лише цей точний префікс визначає серію (до 26 входжень). Видалення серії — послідовність атомарних операцій; при збої явно повідомляється прогрес, повтор пропускає виконані входження. Відкриту подію видаляємо останньою, щоб сторінка лишалася доступною для повтору.
- Фізичне видалення документа rooms дозволене admin лише для архівної локації з точним атомарним audit `delete-<roomId>-<revision>`. Клієнт перед операцією перевіряє всі її pending/approved заявки та відмовляє, доки вони не оброблені; повторне відкриття локації змінює revision й відхиляє застаріле видалення. Історичні скасовані/видалені заявки й технічні записи не каскадно знищуються.
- Правила самостійної публікації не послаблюють перевірки часу, зайнятості, публічної проєкції та історії. Повторне обчислення ролі всередині переходу усунено для дотримання ліміту 1000 expressions Firestore.

## Поля розкладу — 22.10.2026

У booking та publicEvents додано необов’язкові contactPhone (публічний телефон відповідального, до 32 символів), notes (примітки до 500 символів), directions (унікальні значення з 15 напрямків MI). Старі записи без цих полів читаються з порожніми значеннями; явно некоректні значення відхиляються. Телефон вводиться окремо з попередженням про публічність, з профілю користувача не береться. Це виняток до згаданого вище виключення контактів із публічної проєкції. Проєкція зобов’язана точно відповідати заявці. Кілька обраних напрямків фільтрують події за збігом хоча б одного; інтервал дат і локація застосовуються одночасно.
